
# 마중 웹 화면 및 사용자 이용 흐름

마중 모바일 웹은 운전자와 탑승자가 휴대전화 브라우저에서 계정과 픽업을 관리할 수 있도록 제공하는 서비스 화면이다.

별도 앱 설치 없이 카카오 로그인, 사람 검색, 마중 요청, 초대 링크 참여, 픽업 상태 확인 및 차량 계정 연결을 이용할 수 있다.

이 문서는 주요 화면의 역할, 사용자 흐름, 실시간 상태 갱신, 연결 복구 및 화면 검증 범위를 설명한다.

---

## 1. 첫 접속과 서비스 시작

처음 마중 웹에 접속하면 서비스 이용 방법을 안내한다.

일반 사용자는 카카오 로그인 후 계정 및 픽업 기능을 사용할 수 있다.

반면 기존 픽업 초대 링크를 받은 탑승자는 해당 링크를 통해 바로 픽업 참여 화면으로 이동한다.

### 시작 경로

| 접속 방법 | 동작 |
| --- | --- |
| 일반 홈 접속 | 서비스 소개 및 시작 방법 안내 |
| 계정 페이지 접속 | 카카오 로그인 및 계정 기능 |
| 픽업 초대 링크 | 해당 픽업 참여 화면 |
| 차량 최초 연결 QR | 로그인 후 차량 등록·계정 연결 |
| 기존 차량 계정 연결 QR | 로그인 후 등록된 차량의 계정 연결 |

각 흐름의 인증과 접근 권한은 서로 구분한다.

픽업 초대 링크를 통한 탑승자 참여에 차량 등록이나 운전자 계정 연결을 요구하지 않는다.

---

## 2. 로그인 후 주요 화면

로그인 후에는 세 가지 주요 화면을 사용한다.

| 화면 | 주요 기능 |
| --- | --- |
| 픽업 | 초대·보낸 요청·대기열·현재 픽업 |
| 사람 찾기 | 운전자 검색·마중 요청·사람 연결 |
| 내 정보 | 계정 정보·닉네임·차량 연결 관리 |

### 픽업

사용자가 참여 중이거나 요청한 픽업을 확인한다.

주요 정보:

- 현재 진행 중인 픽업
- 받은 초대
- 내가 보낸 마중 요청
- 운전자 응답 대기
- 수락된 요청의 대기 순서
- 픽업 종료 상태

여러 항목이 존재하면 **진행 중인 픽업을 우선 표시**한다.

요청 수락과 실제 픽업 시작은 다른 상태로 구분한다.

### 사람 찾기

운전자 닉네임이나 마중 ID로 계정을 검색한다.

사용자는 다음 작업을 할 수 있다.

- 닉네임 부분 검색
- 마중 ID 정확 검색
- 운전자에게 마중 요청
- 지도에서 픽업 장소 선택
- 별도의 사람 연결 요청

기존 사람 연결이 없어도 운전자에게 마중 요청을 보낼 수 있다.

사람 연결 승인이 픽업 생성이나 위치 공개를 의미하지는 않는다.

### 내 정보

본인의 계정과 차량 연결 상태를 관리한다.

주요 기능:

- 마중 ID 확인
- 닉네임 설정·변경
- 운전자 계정에 연결된 차량 확인
- 차량 계정 연결 및 해제

차량의 장치 등록 권한과 운전자 계정 연결은 별도로 관리한다.

---

## 3. 현재 픽업 화면

현재 픽업 화면은 탑승자가 실제 픽업 진행 상황을 확인하는 데 필요한 정보를 우선 표시한다.

### 주요 표시 정보

1. 운전자 정보
2. 확정된 만남 장소
3. 예상 도착 시간
4. 지도 및 차량 위치
5. 탑승자 준비 상태

차량 위치와 ETA는 서버가 제공하는 최신성 상태를 따른다.

오래된 위치를 현재 위치처럼 표시하지 않는다.

### 준비 상태

탑승자는 웹에서 자신의 준비 상태를 변경할 수 있다.

준비 상태가 서버에 전달됐는지 확인하는 표시와, 운전자가 해당 상태를 확인했는지 나타내는 표시는 서로 구분한다.

서버 수신 확인만으로 운전자가 읽었다고 안내하지 않는다.

### 장소 변경 제안

탑승자는 현재 픽업의 다른 만남 장소를 제안할 수 있다.

이때 다음 정보를 구분한다.

- 현재 확정 장소
- 새로 제안한 장소
- 차량의 장소 승인 여부

장소를 제안하더라도 차량에서 경로를 확인하고 확정하기 전까지 기존 장소를 유지한다.

## 4. SSE 기반 상태 갱신

마중 웹은 SSE(Server-Sent Events)를 이용해 픽업의 변경 사항을 감지한다.

SSE는 변경된 상태 전체를 전달하는 용도가 아니라 **상태 변경 신호**로 사용한다.

### 상태 갱신 흐름

```text
서버에서 픽업 상태 변경
           │
           ▼
      SSE 변경 신호
           │
           ▼
       웹에서 수신
           │
           ▼
     관련 API 재조회
           │
           ▼
   최신 상태 및 유효기간 확인
           │
           ▼
         화면 갱신
```

웹은 변경 신호를 받으면 기존 API를 통해 전체 상태를 다시 조회한다.

이벤트 내용을 그대로 최종 상태로 적용하지 않는다.

서버는 SSE 이벤트 이력을 별도로 보관하지 않는다.

### 갱신 중 추가 신호 처리

API 조회가 진행되는 동안 새로운 SSE 신호가 도착할 수 있다.

이 경우 현재 조회가 완료됐다는 이유만으로 새 신호를 지우지 않는다.

새 변경이 발생했다는 사실을 유지하고 다음 갱신 주기에서 다시 조회한다.

이를 통해 연속된 상태 변경 중 일부가 화면에 반영되지 않는 상황을 줄인다.

---

## 5. SSE 연결 유지 및 복구

SSE 연결이 유지되더라도 상태 조회는 별도로 수행한다.

### 정상 연결 상태

SSE를 통해 변경 신호를 수신한다.

이와 별개로 **30초마다 상태를 다시 조회**한다.

이는 연결은 유지됐지만 변경 신호를 놓쳤을 가능성에 대비하기 위한 보완 동작이다.

### SSE 연결 실패

SSE 연결이 실패하면 진행 중인 픽업을 기존 3초 간격 조회 방식으로 확인한다.

| 상태 | 갱신 방식 |
| --- | --- |
| SSE 연결 정상 | 변경 신호 수신 + 30초 주기 재조회 |
| SSE 연결 실패 | 3초 간격 조회로 복구 |
| 인터넷 연결 끊김 | 스트림 종료 및 차량 정보 숨김 |
| 인터넷 재연결 | 최신 상태 조회 후 화면 복원 |

### 스트림 정리

다음 상황에서는 불필요한 SSE 연결을 정리한다.

- 인터넷 연결 실패
- 페이지 숨김 상태
- 로그아웃
- 화면 및 구독 상태 변경으로 연결이 불필요한 경우

SSE를 연결했다고 해서 브라우저를 닫은 뒤에도 상태 변경 알림이 계속 전달되는 것은 아니다.

앱이 닫혀 있는 동안 새로운 마중 요청을 푸시로 알려주는 기능과는 별개다.

## 6. 인터넷 연결이 끊겼을 때

로그인한 픽업 화면도 브라우저의 인터넷 연결 끊김 이벤트를 받으면 기존 차량 정보를 계속 표시하지 않는다.

### 연결 끊김 처리

1. 인터넷 끊김 감지
2. SSE 연결 종료
3. 화면의 차량 위치 숨김
4. 기존 ETA 숨김
5. 연결 상태 안내 표시

네트워크가 끊어진 뒤 마지막 위치를 현재 위치처럼 유지하지 않는다.

### 연결 복구

인터넷 연결이 복구되면 서버에서 최신 상태를 다시 조회한다.

조회가 성공해 유효한 차량 정보가 확인된 이후에만 위치와 ETA를 다시 표시한다.

재연결 사실만으로 과거 정보를 복원하지 않는다.

### 늦게 도착한 응답 차단

인터넷이 끊기기 전에 시작한 API 요청이 뒤늦게 완료될 수 있다.

이전 요청의 응답이 연결 끊김 이후에 도착하더라도 차량 위치와 ETA를 다시 표시하지 않는다.

새로운 연결 상태에서 확인한 최신 응답을 기준으로 화면을 갱신한다.

### 작성 중인 요청 보존

탑승자가 마중 요청을 작성하던 중 인터넷이 끊기면 다음 입력 정보는 유지한다.

- 선택한 만남 장소
- 작성한 장소 설명

다만 요청을 자동으로 다시 전송하지 않는다.

사용자가 연결 상태와 요청 결과를 확인한 후 직접 진행하도록 한다.

## 7. 차량 정보 최신성 표시

서버는 차량 위치·ETA의 최신성 상태를 제공한다.

웹은 해당 상태와 정보의 유효기간을 기준으로 화면을 표시한다.

| 상태 | 처리 |
| --- | --- |
| `FRESH` | 최근 차량 위치 및 ETA 표시 |
| `STALE` | 마지막 정보를 오래된 값으로 구분 |
| `WAITING` | 유효한 차량 정보가 없음을 표시 |

서버가 위치·ETA를 더 이상 제공하지 않으면 웹에서도 이전 값을 숨긴다.

차량 ETA가 0초가 됐다는 이유만으로 픽업을 도착 상태로 변경하지 않는다.

실제 도착 표시는 서버의 `ARRIVED` 상태를 기준으로 한다.

## 8. 첫 이용 안내 및 개인정보

마중은 사용자가 기능을 시작하기 전에 필요한 정보를 확인할 수 있도록 안내 화면을 제공한다.

### 안내 진입 위치

- 서비스 홈
- 초대 참여 화면
- 계정 화면

사용자는 위치 공유와 데이터 보관에 대한 안내를 확인할 수 있다.

### 안내 내용

초대 참여 버튼 앞에서는 해당 픽업에서 공유되는 정보를 설명한다.

로그인 버튼 앞에서는 계정에서 사용하는 정보의 범위를 설명한다.

이 과정에서 강제 팝업이나 새로운 동의 이력 수집 기능은 추가하지 않았다.

### 운영 및 문의 정보

| 항목 | 내용 |
| --- | --- |
| 운영 주체 | 송승준 · 개인 |
| 공개 문의 | john091122@naver.com |

이용 안내 화면을 추가했다는 사실만으로 모든 개인정보 처리방침이나 차량 첫 사용 동의 절차가 완료됐다고 판단하지 않는다.

관련 정책 및 실제 사용 조건은 별도로 검토한다.

## 9. 차량 최초 연결

일반 운전자는 차량 QR을 휴대전화로 열어 최초 등록과 운전자 계정 연결을 진행할 수 있다.

### 연결 주소

```text
/account#enroll/{id}/{code}
```

### 처리 흐름

1. 차량에 최초 연결 QR 표시
2. 휴대전화에서 QR 열기
3. URL fragment의 연결 정보 확보
4. 주소에서 원본 fragment 제거
5. 필요한 정보를 해당 탭의 `sessionStorage`에 임시 저장
6. 카카오 로그인 및 닉네임 설정
7. 휴대전화에서 연결 요청
8. 차량에서 닉네임·마중 ID 확인
9. 차량 승인 후 연결 완료

휴대전화에서 연결 요청을 보낸 것만으로 차량 등록이 완료되지 않는다.

차량 화면의 최종 확인이 필요하다.

### 연결 대기 및 취소

차량에서 승인이 완료되기 전까지 웹에는 연결 대기 상태를 표시한다.

사용자가 휴대전화에서 취소하면 해당 연결 요청을 종료한다.

취소된 QR을 다른 계정의 연결 요청에 재사용하지 않는다.

### 보안

QR 연결 코드는 URL fragment에서 읽은 뒤 주소에서 제거한다.

OAuth2 로그인 왕복에 필요한 정보는 `sessionStorage`에만 임시 보관한다.

차량 장치 비밀은 웹에서 받거나 저장하지 않는다.

관리자 등록 코드 입력은 일반 사용자 최초 연결 화면에 포함하지 않는다.

---

## 10. 기존 차량의 계정 연결

이미 등록된 차량은 별도의 계정 연결 QR을 사용할 수 있다.

### 연결 주소

```text
/account#vehicle/…
```

이 경로는 기존 차량을 운전자 계정에 연결하는 데 사용한다.

최초 차량 등록 QR과는 처리 목적이 다르다.

| 구분 | 최초 차량 연결 | 기존 차량 계정 연결 |
| --- | --- | --- |
| QR 경로 | `#enroll/…` | `#vehicle/…` |
| 대상 | 아직 최초 연결되지 않은 차량 | 이미 등록된 차량 |
| 카카오 로그인 | 필요 | 필요 |
| 휴대전화 연결 요청 | 필요 | 필요 |
| 차량 최종 확인 | 필요 | 필요 |
| 관리자 코드 | 일반 사용자에게 요구하지 않음 | 요구하지 않음 |

두 흐름 모두 차량에서 요청자의 계정을 확인해야 완료된다.

## 11. 화면 및 브라우저 검사

### 로컬 미리보기

로컬 웹 서버 실행 후 다음 경로에서 화면을 확인할 수 있다.

```text
http://127.0.0.1:4173/preview/account
http://127.0.0.1:4173/preview/pickup
```

기준 화면 크기:

```text
390 × 844
```

미리보기는 CSS 화면 배치와 크기를 확인하기 위한 도구다.

실제 휴대전화와 모바일 브라우저의 동작 검증을 대체하지 않는다.

### 통합 확인

실제 카카오 지도 SDK와 가상 로그인 계정을 이용한 로컬 브라우저 시험에서 다음 항목을 확인했다.

- 픽업 화면 표시
- SSE 연결
- 변경 신호 처리
- 새로운 ETA 표시

### 자동 테스트

주요 테스트 파일:

```text
account-refresh.test.js
stream.test.js
```

검증 항목:

- 주요 메뉴 이동
- 서버 상태 갱신 신호 처리
- 기존 주기 조회 방식으로 복구
- API 인증 헤더 처리

테스트의 실행 환경과 실제 모바일 기기 검증은 구분한다.

## 12. 현재 검증 범위와 제한

### 확인한 범위

- 주요 모바일 웹 화면 구성
- 가상 로그인 기반 계정 화면
- 실제 지도 SDK 연동
- SSE 상태 갱신
- ETA 화면 표시
- 네트워크 연결 끊김 시 정보 숨김
- 늦게 도착한 이전 응답 차단
- 작성 중인 마중 요청 정보 유지
- QR 로그인 복귀 처리

### 별도 검증 항목

- 실제 휴대전화의 모바일 브라우저 동작
- 실제 GPS 권한 및 위치 정확도
- LTE·Wi-Fi 전환 중 상태 복구
- 휴대전화 잠금 화면과 백그라운드 알림
- 장시간 네트워크 단절
- 실차와의 전체 픽업 흐름

로컬 브라우저 시험과 CSS 미리보기 결과를 실제 휴대전화 검증 완료로 기록하지 않는다.
