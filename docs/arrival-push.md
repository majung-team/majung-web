
# 도착 임박 웹 푸시 알림

마중 모바일 웹은 차량이 탑승자의 약속 장소에 약 3분 이내로 접근했을 때 브라우저 푸시 알림을 받을 수 있도록 지원한다.

탑승자가 알림 권한을 허용하고 해당 픽업에 푸시를 구독하면, 브라우저 화면을 닫거나 다른 앱을 사용하는 중에도 운영체제와 브라우저가 허용하는 조건에서 알림을 받을 수 있다.

알림은 **픽업당 최대 한 번 발송을 시도**하며, 실제 알림 도착을 보장하지는 않는다.

이 문서는 기능 7.1의 웹 화면, 구독·해제, 서비스 워커, 브라우저별 제한 및 배포 검증 결과를 설명한다.

서버의 발송 조건과 VAPID 키 설정은 [백엔드 도착 임박 웹 푸시](https://github.com/majung-team/majung-backend/blob/main/docs/arrival-push.md)를 따른다.

---

## 1. 기능 개요

| 항목 | 동작 |
| --- | --- |
| 알림 조건 | 차량 ETA 약 3분 이내 |
| 기본 임계값 | 180초 |
| 표시 화면 | 초대 링크 픽업·계정의 진행 중 픽업 |
| 구독 시작 | 사용자가 직접 `도착 알림 받기` 선택 |
| 구독 해제 | `알림 끄기` |
| 알림 내용 | 서비스 워커의 고정 문구 |
| 발송 횟수 | 픽업당 최대 한 번 시도 |
| VAPID 미설정 | 알림 카드 숨김 |
| 픽업 도착·종료 | 알림 카드 숨김 |

웹은 알림을 구독하고 해제하는 역할을 한다.

ETA가 임계값 이하인지 판단하고 실제 푸시 서비스를 호출하는 작업은 백엔드에서 수행한다.

## 2. 알림 카드 표시

알림 카드는 픽업이 `ACTIVE` 상태일 때 표시한다.

### 제공 화면

- 초대 링크 픽업 화면(`/`)
- 로그인한 계정의 진행 중 픽업 화면(`/account`)

두 화면은 동일한 알림 상태 표시 정책을 사용한다.

### 표시 조건

다음 조건을 확인한다.

1. 픽업이 `ACTIVE` 상태
2. 서버의 Web Push 기능 활성화
3. 브라우저의 푸시 지원 여부 확인
4. 브라우저 알림 권한 확인

### 서버 기능 활성화 확인

```http
GET /api/v1/config
```

서버가 제공하는 `webPushPublicKey`를 확인한다.

| 응답 | 처리 |
| --- | --- |
| 공개 키 존재 | 브라우저 알림 기능 표시 가능 |
| `null` | 알림 카드 표시하지 않음 |

VAPID 키가 없더라도 기존 픽업 화면과 차량 정보 공유 기능은 그대로 유지한다.

## 3. 알림 상태별 UI

브라우저 지원 여부와 구독 상태에 따라 카드 내용을 구분한다.

| 상태 | 화면 |
| --- | --- |
| 알림 꺼짐 | 기능 설명 및 `도착 알림 받기` |
| 알림 켜짐 | 발송 안내 및 `알림 끄기` |
| 알림 권한 차단 | 브라우저 설정에서 알림 허용 안내 |
| iPhone 일반 브라우저 탭 | 홈 화면에 추가한 앱에서 사용하도록 안내 |
| 푸시 미지원 | 화면에서 직접 픽업 상태 확인 안내 |
| 픽업 `ARRIVED` | 알림 카드 숨김 |
| 픽업 종료 | 알림 카드 숨김 |

### 알림 활성화 상태

구독이 완료되면 다음 내용을 안내한다.

> 도착 약 3분 전에 알림을 보낼게요. 알림은 한 번만 보내요.

이 문구는 알림을 받을 수 있도록 구독했다는 안내다.

실제 알림 전달 성공을 보장한다는 뜻은 아니다.

## 4. 알림 구독 흐름

탑승자가 `도착 알림 받기`를 선택하면 브라우저 알림 권한과 푸시 구독을 처리한다.

### 처리 순서

1. `도착 알림 받기` 선택
2. 브라우저 알림 권한 확인
3. 필요한 경우 권한 요청
4. 서비스 워커 등록·사용
5. VAPID 공개 키로 푸시 구독 생성
6. 구독 endpoint 확보
7. 백엔드에 구독 등록
8. 구독 성공 상태 표시

### 구독 요청

초대 링크 기반 픽업:

```http
PUT /api/v1/pickups/{id}/arrival-push
```

로그인 계정 기반 픽업:

```http
PUT /api/v1/ride-requests/{id}/arrival-push
```

요청 예시:

```json
{
  "endpoint": "https://fcm.googleapis.com/..."
}
```

성공 응답:

```json
{
  "subscribed": true
}
```

초대 기반 픽업은 해당 픽업의 접근 토큰을 사용한다.

계정 기반 픽업은 로그인 세션 및 CSRF 검증을 사용한다.

서버는 해당 픽업에 알림을 등록할 권한이 있는지 확인한다.

---

## 5. 알림 해제

탑승자가 `알림 끄기`를 누르면 해당 픽업의 구독을 해제한다.

### 처리 대상

- 서버에 저장된 픽업 구독
- 브라우저의 PushSubscription

### 구독 해제 API

초대 기반 픽업:

```http
DELETE /api/v1/pickups/{id}/arrival-push
```

계정 기반 픽업:

```http
DELETE /api/v1/ride-requests/{id}/arrival-push
```

성공 응답:

```json
{
  "subscribed": false
}
```

서버 구독 정보와 브라우저 구독 상태는 서로 다른 저장 위치에서 관리된다.

따라서 구독 해제 이후에는 두 상태가 일치하는지 확인해야 한다.

### 다른 픽업과의 관계

같은 브라우저에서 여러 픽업을 연속으로 이용하면 브라우저의 푸시 endpoint를 재사용할 수 있다.

하지만 서버는 픽업별로 구독 정보를 관리한다.

새 픽업을 시작했다고 해서 이전 픽업의 알림 구독이 자동으로 새 픽업에 연결되는 것은 아니다.

새로운 픽업에서는 다시 `도착 알림 받기`를 선택해야 한다.

## 6. 서비스 워커

마중은 서비스 워커를 통해 푸시 이벤트를 수신하고 사용자 알림을 표시한다.

구현 파일:

```text
sw.js
```

### 알림 내용

현재 푸시 요청에는 사용자별 메시지 본문을 싣지 않는다.

서비스 워커에 다음 문구가 고정되어 있다.

```text
마중 · 차량이 약 3분 안에 도착해요
```

푸시 서비스를 통해 탑승자 이름, 차량 위치, 픽업 장소 또는 ETA 원문을 전달하지 않는다.

### 알림 클릭

알림을 누르면 다음 순서로 처리한다.

1. 관련 브라우저 창 확인
2. 이미 열린 창이 있으면 해당 창으로 이동
3. 열린 창이 없으면 `/account` 열기

실제 이동 후 해당 사용자의 픽업 접근 여부는 기존 인증과 접근 권한 정책을 따른다.

서비스 워커가 알림을 받았다는 이유만으로 픽업 접근 권한을 추가하지 않는다.

## 7. 웹 매니페스트

파일:

```text
manifest.webmanifest
```

웹 매니페스트는 마중 웹을 홈 화면에 추가할 수 있도록 필요한 앱 정보를 제공한다.

특히 iPhone의 웹 푸시 사용 조건과 관련된다.

### 현재 구현 범위

- 홈 화면 설치를 위한 매니페스트 제공
- 서비스 워커 기반 알림 표시
- 별도 홈 화면 아이콘은 아직 없음

매니페스트가 있다는 이유만으로 모든 브라우저에서 홈 화면 설치나 푸시 수신이 보장되는 것은 아니다.

## 8. iPhone 및 브라우저별 제한

웹 푸시 지원 조건은 브라우저와 운영체제에 따라 다르다.

### iPhone

iPhone에서는 일반 Safari 탭이 아니라 **홈 화면에 추가한 웹앱**에서 알림을 받아야 한다.

홈 화면 웹앱과 Safari 탭의 저장소 및 세션은 분리될 수 있다.

따라서 현재 구현에서는 iPhone의 로그인 기반 `/account` 흐름을 푸시 사용 대상으로 안내한다.

QR 초대 링크를 Safari 탭에서 열었다는 사실만으로 홈 화면 웹앱의 픽업 구독이 이어지지 않는다.

### 브라우저별 안내

| 환경 | 처리 |
| --- | --- |
| Chrome·Android | 지원 여부와 권한 확인 후 구독 |
| Firefox | 지원 여부와 권한 확인 후 구독 |
| Safari·iPhone 일반 탭 | 홈 화면 웹앱 사용 안내 |
| iPhone 홈 화면 웹앱 | 지원 조건 충족 시 구독 가능 |
| Web Push 미지원 | 알림 대신 화면에서 픽업 확인 안내 |

Firefox와 Safari의 실제 푸시 수신 결과는 아직 확보하지 않았다.

### 알림 표시의 한계

브라우저와 운영체제의 다음 조건에 따라 알림이 지연되거나 표시되지 않을 수 있다.

- 사용자 알림 권한
- 운영체제 알림 설정
- 절전·백그라운드 제한
- 네트워크 연결
- 브라우저 푸시 서비스 상태

초대 링크를 열기만 하면 잠금 화면 알림까지 보장되는 기능은 아니다.

## 9. 중복 발송과 재구독

도착 임박 알림은 픽업당 최대 한 번 발송을 시도한다.

### 서버 발송 조건

기본적으로 다음 조건을 사용한다.

- 픽업 상태 `ACTIVE`
- 유효한 구독 존재
- 차량 ETA 180초 이하
- 해당 픽업의 이전 발송 기록 없음

서버는 `notified_at` 조건부 갱신으로 중복 발송 시도를 제한한다.

### 재구독

알림을 발송 대상으로 처리한 이후 구독을 다시 생성해도 같은 픽업의 알림은 재발송하지 않는다.

### 발송 실패

푸시 서비스 요청이 실패하더라도 자동 재시도하지 않는다.

따라서 구독 완료와 실제 알림 수신은 구분한다.

자세한 서버 정책은 [백엔드 도착 임박 웹 푸시](https://github.com/majung-team/majung-backend/blob/main/docs/arrival-push.md)를 따른다.

## 11. 배포 전 준비

도착 임박 웹 푸시를 사용하려면 서버 설정과 웹 배포 파일 허용 목록이 준비되어야 한다.

### 백엔드 준비

1. VAPID 키 생성
2. 운영 환경변수 설정
3. `arrival_push` 테이블 적용
4. 데이터베이스 실행 계정 권한 확인
5. 새 서버 배포 및 설정 API 확인

VAPID 개인 키는 서버에만 저장한다.

### 웹 정적 파일

다음 파일을 배포 허용 목록에 추가해야 한다.

```text
push.js
sw.js
manifest.webmanifest
```

서버 배포 스크립트:

```text
deploy/release.py
```

운영 서버에 설치된 배포 프로그램:

```text
/usr/local/sbin/majung-deploy
```

허용 목록을 갱신하기 전에 새 파일을 배포하면 알 수 없는 파일로 거부될 수 있다.

### CSP

현재 서비스 워커와 웹 매니페스트는 같은 origin에서 제공한다.

따라서 이번 기능 추가를 위해 운영 Caddy의 CSP 허용 출처를 별도로 변경하지 않았다.

### 권장 반영 순서

1. 운영 DB 백업
2. `arrival_push` 테이블 및 권한 적용
3. VAPID 키 준비
4. 서버 코드 및 설정 반영
5. 웹 배포 파일 허용 목록 갱신
6. 웹 정적 파일 배포
7. 공개 HTTPS에서 설정·파일 응답 확인
8. 브라우저 구독 및 해제 확인
9. 실제 기기 수신 검증

## 12. 자동화 테스트

웹 자동 테스트에서 다음 항목을 확인했다.

### 알림 카드 및 구독

- 구독 상태 판정
- 카드 표시 조건
- 사용자 입력 및 문자열 이스케이프
- VAPID 공개 키 변환
- 브라우저 지원 여부 확인
- iPhone 환경 판정

### 서비스 워커

- 푸시 이벤트 처리
- 고정 문구 알림 표시
- 알림 클릭 처리

### 계정 API

- 장소별 구독 API 경로 허용
- 로그인 세션 요청 처리
- CSRF 토큰 포함

실행 명령:

```sh
npm test
```

해당 테스트는 웹 로직과 서비스 워커 동작을 확인한 결과다.

실제 운영체제의 알림 배너 표시까지 검증했다는 의미는 아니다.

## 13. 로컬 Chrome·FCM 연동 검증

로컬 백엔드와 헤드리스 Chrome을 이용해 실제 FCM 푸시 서비스까지 연동했다.

### 시험 환경

- 로컬 Spring Boot 서버
- 테스트용 VAPID 키
- 헤드리스 Chrome
- 실제 FCM
- 운영 Caddy와 동일한 CSP를 적용한 시험 환경

### 시험 순서

1. 도착 임박 알림 카드 표시
2. 브라우저 알림 권한 허용
3. FCM 푸시 endpoint 구독
4. 서버에 구독 등록
5. 차량 ETA 400초 전송
6. 알림이 발송되지 않는지 확인
7. 차량 ETA 120초 전송
8. Chrome에서 푸시 알림 수신
9. 알림 끄기
10. 구독 해제 확인

### 시험 결과

| 항목 | 결과 |
| --- | --- |
| 알림 카드 표시 | 확인 |
| 브라우저 권한 요청 | 확인 |
| FCM 구독 | 확인 |
| ETA 400초 | 알림 없음 |
| ETA 120초 | 알림 수신 |
| 알림 해제 | 확인 |
| 운영과 동일한 CSP 환경 | 확인 |

이 시험은 실제 FCM 서비스를 이용한 푸시 수신 검증이다.

다만 로컬 서버와 테스트용 VAPID 키를 사용했으며, 실제 휴대전화의 잠금 화면 알림을 확인한 것은 아니다.

## 15. 운영 Chrome 구독 시험

운영 공개 서버에서 가상 픽업을 이용해 Chrome 구독 흐름을 시험했다.

### 확인한 흐름

1. 가상 시험 픽업 생성
2. 알림 권한 허용
3. 브라우저 푸시 구독
4. 서버에 구독 등록
5. 시험 ETA 400초 전송
6. 시험 ETA 120초 전송
7. 알림 구독 해제

### 결과

운영 Chrome에서 권한 요청, 푸시 구독 및 구독 해제까지 확인했다.

하지만 운영체제 알림 배너의 실제 표시를 직접 확인하지 못했다.

따라서 **운영 서버에서 알림 수신이 완료됐다고 기록하지 않는다.**

### 시험 데이터 정리

시험이 끝난 뒤 다음 작업을 수행했다.

- 가상 시험 픽업 취소
- 시험 차량 권한 철회

이 결과는 실제 사용자의 휴대전화나 실차를 이용한 시험이 아니다.

## 16. 지도 서비스 운영 설정

같은 운영 반영 과정에서 카카오맵 관련 설정도 확인했다.

카카오의 무료 쿼터 이관 완료 안내에 따라 마중 전용 앱의 지도 API를 활성화했다.

당시 설정:

- 마중 전용 지도 API 및 JavaScript 키 설정
- 운영 Web 도메인 등록
- 필요한 Caddy CSP 반영
- HANMAP 지도 비활성화
- 유료 월렛 미연결

지도 SDK 연동과 실제 리소스 로딩 검증은 별도 문서에서 관리한다.
