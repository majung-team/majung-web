
# 픽업 장소 변경 제안

마중 모바일 웹은 탑승자가 지도에서 새로운 만남 장소를 선택하거나 장소명·주소를 검색해 운전자에게 변경을 제안할 수 있도록 지원한다.

**장소 제안과 실제 장소 확정은 별개의 단계다.**

웹에서 제안을 전송해도 현재 확정된 픽업 장소는 변경되지 않는다. 운전자가 차량 앱에서 제안을 확인하고 내비게이션 경로를 검증한 뒤 승인해야 실제 장소 변경이 이루어진다.

이 문서는 기능 6.1의 웹 화면, 지도 연동, 입력 검증, 상태 관리 및 통합 테스트 결과를 설명한다.

백엔드 API 및 권한 정책은 [장소 제안 API 문서](https://github.com/majung-team/majung-backend/blob/main/docs/place-proposal.md)를 따른다.

---

## 1. 주요 기능

| 기능 | 설명 |
| --- | --- |
| 지도에서 선택 | 원하는 위치를 눌러 제안 핀 배치 |
| 장소명·주소 검색 | 검색 결과에서 장소 선택 |
| 장소 설명 | 만남 위치를 설명하는 문구 입력 |
| 장소 제안 | 선택한 위치와 설명을 서버에 전송 |
| 제안 확인 | 현재 제안 장소 및 제안자 표시 |
| 제안 취소 | 본인이 등록한 제안 삭제 |
| 운전자 제안 확인 | 운전자가 등록한 장소 제안 표시 |
| 확정 장소 유지 | 차량 승인 전까지 기존 장소 유지 |

제안 기능은 픽업이 진행 중인 `ACTIVE` 상태에서만 제공한다.

지도 SDK를 사용할 수 없는 경우 장소 제안 영역도 숨긴다.

---

## 2. 장소 제안 화면

장소 제안 기능은 다음 화면에서 제공한다.

- 초대 링크로 참여한 픽업 화면(`/`)
- 로그인한 계정의 진행 중 픽업 화면(`/account`)

### 표시 조건

다음 조건을 충족해야 `다른 장소 제안하기` 버튼을 표시한다.

1. 현재 픽업이 `ACTIVE` 상태
2. 지도 SDK 사용 가능
3. 지도 렌더링 완료
4. 해당 픽업에 대한 유효한 탑승자 접근 권한 보유

지도 키가 없거나 SDK 로딩에 실패하면 제안 버튼과 입력 영역을 표시하지 않는다.

### 사용자 흐름

1. `다른 장소 제안하기` 선택
2. 지도 핀 또는 장소 검색으로 위치 선택
3. 장소 설명 확인·수정
4. `제안 보내기` 선택
5. 서버에 장소 제안 저장
6. 화면에 제안 장소 표시
7. 차량의 장소 확인 및 승인 대기

이 과정에서 기존 약속 장소는 변경되지 않는다.

---

## 3. 지도 핀으로 장소 선택

탑승자는 지도를 직접 눌러 새로운 만남 장소를 제안할 수 있다.

### 핀 선택 시작

`다른 장소 제안하기`를 누르면 지도에 초록색 테두리가 표시된다.

이는 지도에서 새로운 장소를 선택하는 상태임을 안내한다.

### 위치 선택

지도를 누르면 해당 위치에 `여기` 핀이 표시된다.

다른 지점을 다시 누르면 기존 핀이 새 위치로 이동한다.

지도에서 장소를 선택한 뒤 바로 서버에 전송하지 않는다.

사용자가 `제안 보내기`를 눌러야 저장된다.

### 장소 설명

사용자는 선택한 지점에 대한 설명을 작성할 수 있다.

예시:

```text
정문 앞
지하주차장 입구
건물 뒤편 승하차 구역
```

장소 설명은 최대 120자까지 입력할 수 있다.

### 입력 검증

다음 상황에서는 제안을 전송하지 않는다.

- 지도 핀을 선택하지 않음
- 장소 설명이 비어 있음
- 허용된 설명 길이를 초과함

사용자에게 전송할 수 없는 이유를 안내한다.

---

## 4. 장소명·주소 검색

지도 핀 선택 외에 장소명이나 주소를 검색하여 위치를 선택할 수 있다.

이 기능은 초기 핀 선택 방식 이후 추가됐다.

### 검색 흐름

1. `다른 장소 제안하기` 선택
2. 장소명 또는 주소 입력
3. 검색 결과 확인
4. 장소명과 주소를 비교하여 선택
5. 해당 좌표로 지도 핀 이동
6. 장소 설명 반영
7. `제안 보내기` 선택

검색 결과를 선택하면 지도 핀과 장소 설명이 변경된다.

단, **검색 결과를 선택한 것만으로 서버에 장소 제안이 저장되지는 않는다.**

### 검색 결과 처리

다음 상황을 구분해 안내한다.

| 상황 | 처리 |
| --- | --- |
| 정상 검색 | 장소명·주소 결과 표시 |
| 검색 결과 없음 | 결과가 없음을 안내 |
| 검색 실패 | 검색 오류 안내 |
| 패널 닫기 | 진행 중인 검색 결과 적용 중단 |
| 지도 핀 직접 선택 | 검색 없이 위치 선택 가능 |

검색 중 패널을 닫았을 때 뒤늦게 도착한 응답이 화면에 적용되지 않도록 처리한다.

### 검색과 핀 선택의 관계

장소 검색과 지도 핀 선택은 같은 장소 제안 기능에 사용한다.

검색으로 선택한 위치를 다시 지도에서 조정할 수 있으며, 최종적으로 선택한 좌표와 설명을 서버에 전송한다.

백엔드에는 기존 `place` 형식의 장소 정보를 전달한다.

## 5. 제안 장소 표시

제안이 등록되면 현재 확정 장소와 제안 장소를 서로 구분해 보여준다.

### 확정 장소

기존 약속 장소는 현재 픽업의 확정 장소로 유지한다.

### 제안 장소

새로 제안한 위치에는 별도의 `제안` 마커를 표시한다.

기존 약속 장소 마커를 제안 마커로 대체하지 않는다.

### 제안자에 따른 화면

| 제안자 | 화면 표시 | 탑승자 취소 |
| --- | --- | --- |
| 탑승자 본인 | `내가 제안한 장소` | 가능 |
| 운전자 | `운전자가 제안한 장소` | 불가능 |

제안 장소의 설명도 함께 표시한다.

### 운전자 제안 변경

운전자가 제안한 장소는 탑승자가 직접 삭제할 수 없다.

다만 탑승자가 새로운 장소를 제안해 기존 제안을 교체할 수 있다.

백엔드는 한 픽업에 한 개의 제안만 유지한다.

---

## 6. 제안 취소와 픽업 상태

### 제안 취소

본인이 등록한 제안에는 `제안 취소` 버튼을 제공한다.

취소하면 서버의 제안 정보가 삭제된다.

기존 확정 장소는 변경되지 않는다.

### 도착 및 종료 상태

픽업이 `ARRIVED` 또는 종료 상태가 되면 새로운 장소 제안 영역을 표시하지 않는다.

백엔드는 `ACTIVE` 상태에서만 새 제안을 허용한다.

기존 제안의 삭제 가능 여부는 서버의 상태 및 접근 권한 정책을 따른다.

### 서버 오류 처리

확정 장소와 같은 좌표를 제안하면 서버에서 `SAME_PLACE` 오류를 반환할 수 있다.

웹은 기존 확정 장소를 변경하지 않고 제안이 거절된 이유를 안내한다.

권한이 없거나 종료된 픽업에도 새로운 제안을 전송하지 않는다.

## 7. 프론트엔드 구현 구조

장소 제안 기능은 기존 JavaScript 기반 웹에 통합했다.

| 파일 | 역할 |
| --- | --- |
| `proposal.js` | 입력 검증, 제안 UI, 설명 패널 |
| `map.js` | 제안 마커 및 지도 핀 선택 |
| `app.js` | 초대 링크 픽업 화면 연동 |
| `account.js` | 로그인 계정의 픽업 화면 연동 |

React 컴포넌트를 사용하는 구조가 아니라 기존 HTML·CSS·JavaScript 렌더링 흐름을 따른다.

### proposal.js

- 제안 영역 표시 조건
- 장소 설명 입력
- 입력값 검증
- 제안 버튼 및 취소 버튼
- 제안 상태에 따른 안내 문구

### map.js

기존 지도 객체에 장소 제안 정보를 전달한다.

주요 기능:

- `update(..., proposal)`
- `startPicking`
- `stopPicking`

`update`는 확정 장소와 제안 마커를 구분해 표시한다.

`startPicking`과 `stopPicking`은 지도에서 제안 위치를 선택하는 상태를 관리한다.

### app.js 및 account.js

초대 링크 화면과 로그인 계정 화면에서 장소 제안 UI를 연결한다.

각 화면은 기존 인증 방식을 유지한다.

## 8. DOM 재사용과 입력 상태 유지

마중 웹은 상태 갱신 과정에서 화면 일부를 다시 렌더링한다.

이때 장소 제안 패널을 매번 새로 생성하면 사용자가 작성 중인 설명이나 입력 초점이 사라질 수 있다.

### 패널 재사용

제안 패널은 처음 필요할 때 한 번 생성한다.

이후 화면이 갱신되면 기존 DOM 요소를 새 위치로 옮겨 붙인다.

### 유지할 상태

- 작성 중인 장소 설명
- 입력창 초점
- 현재 선택한 위치
- 제안 패널의 사용 상태

### 초대 링크 화면의 폴링

장소 설명 입력창에 초점이 있는 동안에는 초대 링크 화면의 주기적인 다시 그리기를 중단한다.

입력창에서 초점이 해제되면 즉시 화면을 갱신한다.

이를 통해 실시간 픽업 상태 갱신과 사용자의 입력을 함께 처리한다.

## 9. 계정 기반 픽업 API 연동

로그인한 사용자의 픽업 화면은 요청 기반 장소 제안 API를 사용한다.

```http
PUT /api/v1/ride-requests/{id}/place-proposal
```

```http
DELETE /api/v1/ride-requests/{id}/place-proposal
```

계정 클라이언트의 허용 API 경로에 해당 경로를 추가했다.

요청에는 기존 로그인 세션과 CSRF 검증을 사용한다.

초대 링크 화면은 해당 픽업에 대한 별도 접근 토큰을 사용한다.

두 화면은 같은 장소 제안 UI를 이용하지만 인증 방식은 구분한다.

[백엔드 장소 제안 API](https://github.com/majung-team/majung-backend/blob/main/docs/place-proposal.md)

## 10. 운전자용 개발 화면

`developmentToolsEnabled`가 활성화된 개발 환경에서는 운전자·탑승자가 등록한 제안을 확인할 수 있다.

개발용 화면에서 제공하는 기능:

- 제안 장소 확인
- 제안자 구분
- `제안 지우기`

실제 운전자는 차량 앱에서 장소 제안을 확인하고 경로를 처리한다.

일반 웹에는 운전자 전용 지도 핀 제안 화면을 별도로 구현하지 않았다.

개발용 UI의 존재를 실제 차량 승인 기능 구현 완료로 해석하지 않는다.

## 11. 배포 전 준비

장소 제안 기능은 웹 코드뿐 아니라 백엔드 DB 구조와 배포 파일 허용 목록에도 영향을 준다.

### 데이터베이스 변경

백엔드의 `pickup` 테이블에 제안 관련 컬럼이 필요하다.

적용 SQL:

```text
src/main/resources/db/add-place-proposal.sql
```

새 서버는 시작 시 DB 구조를 검사하므로 마이그레이션을 먼저 적용해야 한다.

### 웹 배포 허용 목록

새 정적 파일 `proposal.js`를 서버의 웹 파일 배포 허용 목록에 추가해야 한다.

관련 서버 파일:

```text
deploy/release.py
```

운영 서버에 설치된 배포 프로그램:

```text
/usr/local/sbin/majung-deploy
```

허용 목록을 갱신하기 전에 웹을 배포하면 알 수 없는 파일로 거부될 수 있다.

### 적용 순서

1. 운영 DB 백업
2. 장소 제안 컬럼 추가
3. 서버 스키마 검사 및 API 확인
4. 배포 파일 허용 목록 갱신
5. 웹 정적 파일 배포
6. 공개 HTTPS에서 기능 확인

웹 코드만 먼저 운영에 배포하지 않는다.

## 12. 초기 자동화 테스트

장소 제안 기능의 초기 구현에서 다음 항목을 자동화 테스트로 확인했다.

- 장소 설명 입력 검증
- 제안 영역 표시 조건
- 지도 핀 선택
- 제안 마커 표시
- 계정 기반 API 경로 허용

### 가짜 지도 SDK 기반 브라우저 시험

로컬 Chrome에서 지도 SDK 대역 객체와 실제 서버를 연결해 시험했다.

확인한 항목:

- 핀 없이 제안 전송 차단
- 설명 없이 제안 전송 차단
- 폴링 중 입력값 및 초점 유지
- 장소 제안 저장
- 확정 장소 유지
- 운전자 제안으로 교체
- 본인 제안 취소
- 기존 확정 장소와 같은 위치 제안 차단

### 초기 시험의 제한

당시 다음 항목은 아직 검증하지 못했다.

- 실제 카카오맵에서 핀 선택
- 실제 휴대전화 화면
- 로그인 계정 화면의 실제 브라우저 흐름

이후 일부 항목은 2026년 10월 26일 통합 시험에서 추가로 검증했다.

| --- | --- |
| 웹 테스트 | 48건 통과 |
| 계정 화면 회귀 테스트 | 포함 |
| 장소 제안·준비 상태 통합 | 확인 |

실제 계정 화면 코드에서 준비 상태 수신 확인과 장소 제안이 동시에 표시되는 회귀 테스트를 포함했다.

### 브라우저 통합 환경

다음 구성으로 로컬 통합 시험을 수행했다.

- 실제 Spring Boot 서버
- Spring Security
- H2 데이터베이스
- 가상 로그인 계정
- 실제 카카오맵 JavaScript SDK
- 로컬 웹 브라우저

### 확인한 흐름

1. 가상 계정으로 계정 화면 진입
2. 지도에서 제안 위치 선택
3. 장소 설명 입력
4. 장소 제안 전송
5. 서버 저장 확인
6. 확정 장소 유지 확인
7. 제안 취소
8. 준비 상태 및 수신 확인 유지

준비 상태를 변경하거나 차량 수신 확인을 처리해도 제안 장소와 확정 장소가 유지됐다.

반대로 장소 제안을 취소하더라도 준비 상태와 수신 확인이 변경되지 않았다.

### 시험 화면

![실제 카카오맵 SDK와 로컬 통합 API](media/proposal-integration-local.png)

위 이미지는 실제 카카오맵 SDK를 사용한 로컬 통합 시험 화면이다.

계정·픽업·좌표는 가상 시험 데이터이며 운영 서버의 실제 사용자 정보가 아니다.

### 검증 결과 해석

이 시험은 로컬 통합 브랜치에서 수행했다.

테스트 통과만으로 `main` 병합 또는 운영 배포까지 완료됐다고 판단하지 않는다.

## 14. 장소명·주소 검색 추가 검증

초기 장소 제안 기능은 지도 핀 선택을 중심으로 구현했다.

이후 계정 화면과 초대 링크 화면에서 장소명·주소 검색도 지원하도록 확장했다.

### 실제 SDK 연동

로컬 가상 계정에서 실제 카카오맵 SDK를 이용해 다음 흐름을 확인했다.

1. 서울역 검색
2. 검색 결과 선택
3. 지도 핀 및 장소 설명 변경
4. 선택 직후 서버 상태 확인
5. `제안 보내기` 실행
6. 서버 제안 저장 확인
7. 기존 확정 장소 버전 유지 확인

### 확인 결과

검색 결과를 선택한 직후에는 서버에 새로운 장소 제안이 저장되지 않았다.

명시적으로 `제안 보내기`를 실행한 뒤 제안 정보가 저장됐다.

제안 전송 이후에도 기존 확정 장소의 버전은 유지됐다.

또한 검색 도중 패널을 닫으면 늦게 도착한 검색 결과를 적용하지 않도록 처리했다.

## 15. 차량 승인 및 장소 확정과의 구분

기능 6.1의 웹 장소 제안과 기능 6.2의 차량 장소 확정은 서로 다른 처리 단계다.

| 항목 | 웹 장소 제안 | 차량 장소 확정 |
| --- | --- | --- |
| 장소 선택 | 웹 지도·검색 | 차량에서 제안 확인 |
| 서버 제안 저장 | 수행 | 기존 제안 참조 |
| 현재 확정 장소 변경 | 수행하지 않음 | 승인 후 처리 |
| 내비게이션 경로 검증 | 수행하지 않음 | 차량 SDK에서 처리 |
| 실제 차량 경로 변경 | 수행하지 않음 | 별도 연동 및 검증 대상 |

웹에서 장소를 제안했다고 해서 차량의 목적지가 자동으로 변경되지는 않는다.

차량의 경로 검증과 운전자 승인 여부는 별도로 확인해야 한다.
